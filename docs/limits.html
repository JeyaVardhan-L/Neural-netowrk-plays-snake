Chapter 14

Bugs, gaps and the ceiling

Every game ends the same way: the snake walks into a pocket of its own body that it had no way to see. Here is that, plus every bug I hit along the way.

Entry 14 · what is broken, what is missing, what I would do next

How it dies

All 100 evaluation games end with the snake hitting its own body. None hit a wall and none time out. To see why, I took a real game played by the trained model (seed 6, score 28) and kept its last 37 frames. For each frame the figure also computes something the network never sees: how many free cells the head could still reach after each of the three moves, by flood fill.

Frame 34 is the whole problem in one picture. There is danger ahead, so the choice is right or left. Turning right leads to 354 free cells. Turning left leads to 1. To the network the two moves look almost the same: Q = 2.16 for right and 2.21 for left, a difference of 0.06. Its inputs say the same thing about both sides, "no danger", and the only input that separates them is the direction of the food. It turns left, into a pocket, and crashes three moves later.

I checked whether this one game is typical. Measuring all 100 evaluation games the same way, the snake is trapped (it can reach fewer free cells than its own length) a median of about 4 steps before it crashes, between 1 and 20. During those last steps a danger input is usually on, because the snake is sliding along its own body. But a danger input only ever says "this one cell is blocked". It never says "this side is a dead end", and that is the information the decision needed.

This is the ceiling from chapters 12 and 13, seen up close. A policy that only knows about the three neighbouring cells cannot tell an open field from a pocket. No amount of training fixes that. It is a property of the inputs, not of the learning.

The bug and fix ledger

Everything that went wrong while I built this, in order. I kept it because the mistakes taught me as much as the parts that worked.

  • fixed
    No pip on the system Python. Ubuntu's Python 3.14 has no pip or ensurepip, so python3 -m venv failed. Created the venv with --without-pip and bootstrapped pip into it (chapter 1).
  • fixed
    Working out why a game ended, after the fact. My first evaluation code reconstructed the end reason from the final position. It was fragile: it had to recheck walls, bodies and the time-out counter, in the right order. I replaced it with game.end_reason, set at the exact line where the game ends.
  • fixed
    A misleading median. train.py printed the median with :.0f, so 25.5 showed as "26", and I copied "26" into a commit message before noticing. Now it prints one decimal. The commit message still says 26; the real median is 25.5.
  • fixed
    An f-string that only parsed on Python 3.12+. I wrote f"{stats["median"]}", with double quotes inside double quotes. That is legal since 3.12 but a syntax error before it. Switched to single quotes inside; CI now tests 3.10 to 3.13.
  • fixed
    Overclaiming in my own journal. I first wrote that γ = 0 agents "wander and occasionally eat", and that the network "always turns away from danger". I also wrote that the snake is typically doomed many steps before it dies while all its danger inputs read 0. All three were guesses. Re-running and counting showed: four of five γ = 0 seeds circle until they time out; the turn-away habit holds in all 23 disagreements with one-sided danger but not in every such position; and the snake is trapped a median of about 4 steps before the crash, usually with a danger input on. The text now says exactly that. Lesson: measure before you explain.
  • fixed
    Figures that could not light up. In the guide, I set SVG fill attributes on circles that also had a CSS class. A CSS rule beats a presentation attribute, so the nodes would never have changed colour. Caught on review; fixed by setting style.fill.
  • fixed
    Overlapping chart labels. The README charts first had end labels on top of each other and two grey lines that looked identical. Added label spreading and different dash patterns.
  • gap
    The time-out is not Markov. The snake cannot see how long it has gone without food, so from its point of view the time-out is random. I treat it as truncation (not terminal, reward 0) so it does not poison the values, but a cleaner design would add "steps since food" to the inputs or remove the limit once the agent is trained.
  • gap
    Max overestimation. The target takes a max over noisy Q estimates, which is biased upwards. Double DQN fixes this by choosing the action with the online network and evaluating it with the target network. I did not implement it.
  • gap
    Evaluation noise. One 100-game evaluation of one model moves by a couple of apples depending on the board seed (26.43 and 28.46 for the same model). The comparisons in this guide use 5 seeds, but some reported differences (γ = 0.5, lr 0.0001) are still unproven.
  • risk
    Other machines give slightly different numbers. The run is deterministic on my machine. NumPy builds with different maths libraries can differ in the last bits of a float, which can change a tie somewhere and send the run down a different path. Expect the same range, not the same digits.

What I would do next

In order of how much I think each would help:

  1. Let it see space. Add, for each of the three moves, the number of cells reachable after taking it (the flood fill from the figure above), scaled by the snake's length. This directly targets the failure in every game.
  2. Let it see its tail. Add the direction to the tail. Following your own tail is the classic safe strategy for a long snake.
  3. A local view. Replace the danger bits with a small window of cells around the head, say 7 × 7. The network would need more hidden units and more games, but would no longer depend on my hand-picked features.
  4. The whole board with a CNN. The general solution, and a much bigger project.
  5. Double DQN and a Huber loss (squared error for small errors, linear for big ones), which make bigger versions of this more stable.

The first one is maybe 20 lines in get_state, plus changing the input size from 11. If you are using this guide to build your own, that is the first experiment I would try.

IN:What are the limitations of your agent, and how would you improve it?
OUT:

Its inputs only describe the three cells next to the head, so it cannot see when a turn leads into a pocket of its own body. Every evaluation game ends in a body collision, and in replays the snake is doomed several moves before any danger input lights up. My ablations confirmed the ceiling is the representation: very different learners all plateau around 25 to 30.

The first fix is in the inputs, not the network: add the reachable free space for each move, and the direction of the tail. After that, a local grid view or a CNN on the full board, and algorithm upgrades like Double DQN and a Huber loss.
